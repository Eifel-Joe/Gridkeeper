# Round 60: Gridkeeper 1.5.0, German

The add-in speaks German when Fusion is set to German, English otherwise. The docs site gets a German version with a
language switcher. Git, code, commit messages and PRs stay English.

## Prior art

GridfinityGenerator (remote `upstream`, as of fadbd128) and the fork `tache` have no translations and don't read
Fusion's language (`git grep -i "userLanguage\|i18n\|gettext\|translat"` finds only geometric translations). Nothing
to credit for this round beyond the usual credits.

## 1. Add-in texts

### Problem
Every text of the add-in is an English literal in the code: command names and descriptions in the menu, dialog input
names, tooltips, group titles, dropdown items, message boxes, the error window, the HTML pages shown in dialogs and
palettes (compartment layout, custom shape, baseplate layout, settings window, button rows, info pages, snapshot test
report, model pictures palette), the update dialogs and the export dialog. About 45 message boxes, ~170 dialog inputs,
~85 tooltips, 8 HTML pages.

### Options for the text tables

| | A: English text is the key (gettext style) | B: symbolic keys, `en.json` and `de.json` |
|---|---|---|
| Code | `_('Bin type')`, the English stays readable where it is used | `t('bin.binType')`, English moves to a table |
| Diff | wraps literals, ~1 line per text | every text moves, larger diff, harder review |
| Merging upstream changes | upstream code still looks like ours | every upstream text change needs a key |
| Changing an English text | the German entry no longer matches, the completeness test fails and names it | silent, the key stays |
| Same English word, two meanings | a context: `_('Label', 'container')` | separate keys |

**Decision: A.** One source per language: English in the code (`_()` calls), German in `lib/i18n/de.json`
(English text → German text, with an optional context prefix `context|text`). A test collects every `_()` call by
parsing the add-in's Python files (AST, string literals only) and every `data-i18n` text of the pages, and fails on
- an English text without a German entry,
- a German entry no code uses any more (stale),
- different `{placeholders}` in English and German,
- a `_()` call with a non-literal argument (texts built at runtime can't be checked; such places pass the parts
  through `_()` and format them).

### Which language
- At add-in start, `lib/i18n.language()` reads `app.preferences.generalPreferences.userLanguage`. German
  (`adsk.core.UserLanguages.GermanLanguage`, compared by the enum name, not a number) gives `de`, every other language
  and every error (old Fusion, no preferences) gives `en`. Fusion needs a restart after its language changes, so the
  add-in reads it once.
- A file `languageOverride` in the add-in folder (ignored by git, like `updateConfig`) holding `de` or `en` wins over
  Fusion's setting. For testing German without restarting Fusion in another language, and for whoever wants English in
  a German Fusion. Documented on the developers page only.
- A German text missing at runtime falls back to the English one (the test keeps this from happening in a release).

### Values stay language-neutral
- Dropdown items show `_(value)`, the command state, `ui_input_defaults.json`, saved settings files, the config tags
  in documents and `api.py` keep the English value. One helper adds items (`dropdowns.addItem(dropdown, value, ...)`)
  and one reads them (`dropdowns.value(input)`), `CommandUiState` and `settingsUtils` use it; the 13 places reading
  `selectedItem.name` go through it. Names from data (printers, filaments, fonts, symbols) aren't translated and come
  back unchanged. A test checks no German label of one value equals another value.
- A document built in German rebuilds, clones and exports the same in English and back.
- **Settings window record**: the tag keeps the dialog's labels and values as text (the *Gridkeeper settings*
  window shows them). Decided: it stays a record in the language the part was built in. The window's own frame
  (title, buttons) follows the current language.
- **Names in the model** stay English: components (*Bins*, *Grid*, *Label*, *Boxes*, *Text*, *Box*, *Lid*), bodies,
  sketches, features, user parameters, joint origins, appearances. Some are found by name, parameter names are
  identifiers, and a document is shared between people with different languages. Exported file names come from
  component names and stay English too.

### Numbers
Fusion's own value inputs show numbers the way Fusion does. Numbers in the add-in's own texts (tooltips such as
*Total bin width: 83.5mm*, messages, the settings window) use a decimal comma in German (`i18n.number()`). Expressions
the user types or that go into Fusion stay as they are.

### Pages (HTML)
Pages get their texts with the data they already get: `browserPages.encode` adds `strings` (the page's texts in the
current language), `fusionBridge.js` replaces the text of elements with `data-i18n="English text"` and fills
`data-i18n-title` and placeholders. Texts the page's script builds use `fusionBridge.t('English text')`. The English
text stays in the HTML, so a page without data (opened in a browser, the screenshot tool before the first message)
reads English.

### Scope of translation
Everything the user sees: menu entries and descriptions (Create panel, context menu, Utilities), dialogs and their
tooltips, message boxes, the error window, progress dialogs, the update dialogs, the export dialog and its notes,
pages, the settings window.

**Decided:** the development commands (*Gridkeeper tests: run*, *Gridkeeper docs: render models*, only in a git
checkout) stay English with their windows and the test report; the completeness test leaves their folders out, the
docs' snapshot report picture stays English.

**Error reports** (decided): the message and the window are German; the report text meant for a GitHub issue
(summary, add-in and Fusion version, traceback) stays English so maintainers can read it.

Not translated: log lines (`futil.log`, text command window), file content (3MF metadata, Bambu project), code
comments, `api.py` errors raised to scripts (a script author reads Python, English like the API).

## 2. Docs site

### Problem
The docs (`docs/`, mkdocs with Material, ~23,000 words on 27 pages) are English only.

### Options
| | A: mkdocs-static-i18n, suffix structure | B: a second mkdocs project in `docs-de/` |
|---|---|---|
| Files | `bins/size.de.md` beside `bins/size.md` | a copied tree |
| Switcher | Material's language selector, set by the plugin | hand-made links |
| Nav titles | `nav_translations` in `mkdocs.yml` | a second `mkdocs.yml` |
| Missing German page | falls back to English | broken link |

**Decision: A**, `mkdocs-static-i18n` (pinned in `pages.yml` beside `mkdocs-material~=9.5`). English stays the default
at the site root, German under `/de/`. The switcher in the header goes to the same page in the other language.
Search works per language. `mkdocs build --strict` stays green.

### Pictures
As decided: model pictures and hover pictures (no text) are shared. Dialog pictures (`docs/assets/images/dialog-*.png`,
`docs/assets/ui`), animations of dialogs in `docs/assets/gif`, and windows of the add-in (settings window, context
menu, update dialogs) get a German version, `name.de.png` / `name-dark.de.gif` beside the English
one, referenced by the German pages. Pictures of Fusion's own interface (Scripts and Add-Ins, Change Parameters,
browser, joints) stay English for now. A German picture not made yet: the German page shows the English one and the
picture is listed in `docs/assets/images/NEEDED.md`.

Pictures the screenshot tool makes (`tools/screenshots`, headless, the fake Fusion API) get a `--language de` option
(the fake reports German, outputs get the `.de` suffix). Pictures taken in Fusion need the computer and wait for the
main session.

### Text
- Each page translated in full, the German pages name dialog items exactly as `de.json` does.
- *What's new* translated from the changelog (the changelog stays English).
- README and `CHANGELOG.md` stay English; the README links the German docs.
- Credits and license page translated, licenses' own texts stay.

## 3. Release
Version 1.5.0 in `Gridkeeper.manifest`, `CHANGELOG.md` (credits as in the release table), *What's new* in both
languages.

## Not part of this round
- Other languages than German and English (the tables allow adding one: a further `xx.json`).
- Fusion interface pictures in German.
- Translating model names, file names, the settings record of parts already built.
- Choosing the language in a dialog of the add-in.

## End-to-end check
1. `python -m pytest` green, including the completeness test of `de.json` and the dropdown value tests.
2. `mkdocs build --strict` green; the built site has `/de/` for every page, the switcher leads from
   `/bins/size/` to `/de/bins/size/` and back.
3. Fusion with `languageOverride` = `de` (job through the main session, generators called directly, no dialogs):
   a bin, a baseplate, a label, a box and a box label built from saved English defaults; their tags hold the English values; switching
   back to `en`, *Rebuild* and *Clone* reopen them with the same values; the snapshot tests stay green in English.
4. Click test in German (computer, main session): menu entries and hover texts, each dialog, the settings window,
   the export dialog, the update dialog.
5. German dialog pictures of the screenshot tool generated and on the German pages.

## Decisions on the open questions (approved with the spec)
1. Settings record of built parts: stays in the language the part was built in.
2. Error report text for issues: English.
3. Development commands: stay English, windows and report included.
4. Glossary as above, *bin* is *Behälter*.
