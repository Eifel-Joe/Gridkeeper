# Round 59: Gridkeeper 1.5.0

Hover pictures for the label, box and box label commands, export from scripts, and three findings of the snapshot
tests (a box in an inch document, a divider gap check, a check on a bin without walls).

## 1. Hover pictures for label, box and box label

### Problem
Hovering over *Gridkeeper bin* or *Gridkeeper baseplate* in the menu shows Fusion's tooltip with a picture
(`resources/toolclip.png`, from the original, set with `cmd_def.toolClipFilename`). The label insert, box and box label
commands show text only.

### Look of the original's pictures (measured on `commandCreateBin/resources/toolclip.png`)
- 300 × 230 px, RGBA, transparent background, model content 8 px from the left and right edge (margin ≈ 0.03).
- Shaded with visible edges: dark outlines on every edge.
- One turquoise, faces between RGB (74, 155, 184) and (82, 165, 197), no grading.
- Orthographic, from the top right corner (Fusion's isoTopRight).

### Decisions
1. Same look as the original's pictures, not the docs' blue (decided before this round).
2. Rendered in Fusion from presets by script, as the docs' model pictures (`scriptRender.renderRaw` and
   `tools/screenshots/finishPictures.py`), so they can be made again when a model changes. The presets live in a
   folder of their own, `tools/screenshots/toolclips/`, with a base `_toolclip.json` holding the look; the docs'
   presets and their check that every preset is used by a page stay as they are.
3. A preset may name its picture's file (`file`, default the preset's name), so three presets each write a
   `toolclip.png` into their command's `resources`.
4. Contents: label command a Cullenect insert with a screw and its size; box command a box 5 × 4 × 6 with its lid;
   box label command the label of a box 4 cells wide. A sample of the three goes to the main session for approval
   before they are put in.
5. The three `entry.py` set `toolClipFilename` as the bin and baseplate commands do, when the file is there. The menu
   icons (16/32/64 px) stay.

## 2. Export from scripts

### Problem
Scripts in Fusion can build with `import gridkeeper` (`api.py`) but not export. The original (GridfinityGenerator 2.6,
Le0Michine) added `exportBodies` with `ExportOptions`; Gridkeeper's export is built differently (label filaments per
color, Bambu Studio project, plates per file, the notice before saving a project), so that code isn't taken over.

### Decisions
1. `export.exportBodies(bodies=None, folder='', options=None)` in `commands/commandExport/entry.py`, offered in
   `api.py` with `ExportOptions` and `ExportResult` (the original's names and its idea: no dialogs, the dialog's last
   choices where the script gives none, fail on files there already unless told to overwrite).
2. `ExportOptions`: format (3MF, STL, STEP), file name, paint, filaments by label color, printer (by name, as in the
   dialog's list), bed size for a custom printer, spacing, purge, files (one project or a file per plate), overwrite.
   Each left as `None` takes the dialog's last choice. Checked before anything is written; a wrong value raises
   `ValueError` naming it.
3. Bodies: bodies and occurrences as the dialog takes them, `None` for all Gridkeeper parts of the active design.
4. No message boxes, no folder dialog, no progress dialog. Files there already: `FileExistsError` naming them, unless
   `overwrite`. The notice the dialog shows before saving a Bambu Studio project is not asked: the script chose the
   printer and the project; the notice's text goes into the result (`ExportResult.notes`), with the dialog's notes on
   plates and label colors.
5. `ExportResult`: the files written, parts, painted parts, the parts too large for the bed, plates without room for
   the purge tower, plates near an excluded area, project plates, notes.
6. The dialog uses the same export underneath, with its questions and progress bar as before; it alone saves its
   choices. Pure parts (options against the saved choices, checks) in `lib/exportParts.py`, unit tested.

## 3. A box in an inch document splits some faces

### Problem
The snapshot test builds each box in an inch document too. There, base and lid each have 12 small vertical
cylinder faces (six places near the front and right edges, low and high) split in two halves, some faces 0.01 mm off.
Volume and shape are the same. Moving the box's extrusions and cell spacing to mm expressions (1.4.0) didn't fix it.

### Approach
Diagnosis in Fusion first (job `r59_probe.py`): the box `box_4x3x6` in an inch and an mm document, all parameters
compared, the cylinder faces at the places and the timeline features that make them. The value that reaches Fusion as
a number and is kept in inches is then passed as an mm expression (`dim.lengthExpression`), as elsewhere.
Done: the inch build matches the mm snapshot of `box_4x3x6` and `box_5x4x6`.

## 4. Gap between divider and wall at a hollow tab open through the sides

### Problem
Snapshot case `bin_2x1x4_hollow_tab_open_sides` reports a gap of about 3 mm between "the divider" and the outer
wall, 25 mm over the bottom. The bin has one compartment; the check takes a level section's thin stretch of material
for a divider. Known before 1.4.0.

### Approach
Sections of the case in Fusion (job `r59_probe.py`), open and closed sides: whether the print has a gap there (the
tab's floor not reaching the wall) or the check reads the tab's open end as a divider. Then the geometry or the check
is fixed; which one is decided with the result in the plan.

## 5. Gap check on a bin without walls

### Problem
Case `bin_2x1_base_only` (no body, feet only) fails: the gap check cuts a foot and Fusion raises an internal error.

### Decision
The divider gap check returns no note for a bin built without its body (`generateBody` false), as the other checks
that need walls.
